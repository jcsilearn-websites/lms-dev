# ADR 0026: TOTP two-factor sign-in for platform and institution administrators (step 14c)

Status: accepted by the owner. Built in parts, with a review after each:

| Part | Contents                                                                                            | State     |
| ---- | --------------------------------------------------------------------------------------------------- | --------- |
| 0    | Room in the entry chunk (router API imports made dynamic)                                           | built     |
| 1    | Storage, key ring, enrolment by emailed link, sign-in challenge, TOTP, recovery codes, lockout      | built     |
| 2    | Step-up for sensitive actions; replace / disable / regenerate; four-eyes reset; break-glass command | not built |
| 3    | Screens, QR code, E2E; `MFA_ENFORCEMENT=required` becomes the default and production refuses `off`  | not built |

## Context

A platform administrator and an institution administrator are the most powerful identities of the product, and until now a password was all that stood in
front of them (`docs/threat-model.md`, ASVS 2.8). Identity is GLOBAL (`users`, one row per person across colleges), so a second factor belongs to the person,
not to a college.

## Decisions

### Who must use it

- Required: platform administrators (admin host) and institution administrators (their college's host). No grace period: enrolment is forced at the next
  sign-in. No per-college switch. No SMS. No "remember this device".
- Ordinary members and instructors cannot opt in (step 14c).
- Once enrolled, a person is challenged on EVERY host, also where they are an ordinary member.
- `MFA_ENFORCEMENT=required|off` decides whether enrolment is FORCED. An enrolled person is challenged either way. It is `off` by default until Part 3
  (no screens exist before that); from Part 3 on production refuses `off`.
- A college can never reset or remove a second factor: that would change a person's sign-in in other colleges.

### Sign-in

1. The password step creates **no session** when a second step is needed. It answers `202`:
   - `{ "step": "totp" }` for an enrolled person, with a challenge cookie (httpOnly, SameSite=Strict, 5 minutes, bound to the host it was issued on);
   - `{ "step": "enrol_email" }` for a person who must enrol and has not: an enrolment link is e-mailed, no cookie.
2. `POST /api/auth/mfa/verify` with the challenge cookie and `{ code }` or `{ recoveryCode }` creates the session.
3. The database enforces it: `auth_login_complete` (the password path) refuses an enrolled person, and a person who must enrol while enforcement is on. The
   session lookup ignores an administrator's session without `mfa_verified_at` while enforcement is on, so switching enforcement on needs no extra clean-up.

### Enrolment: the emailed link, for platform AND institution administrators

A stolen password must not be enough to enrol the thief's device. The link proves control of the mailbox; the password is asked again on the link page, so the
mailbox alone is not enough either.
- The link lives **30 minutes**, a newer one voids it, and it is used up by a successful confirmation. The worker mints the token when it sends (the outbox
  never holds one), like invites and password resets.
- `POST /api/auth/mfa/enrol/start { token, password }` returns the secret and the `otpauth://` link and sets an enrolment challenge cookie (10 minutes).
  A wrong password counts toward the sign-in lockout.
- `POST /api/auth/mfa/enrol/confirm { code }` (5 tries per challenge) stores the secret, creates 10 recovery codes (shown in this one response), revokes the
  person's other sessions and signs them in.

### TOTP

RFC 6238: SHA-1, 6 digits, 30 seconds (what authenticator apps support), accepted drift **±1 step**. Implemented on `node:crypto` (no dependency),
checked against the RFC vectors. **Replay:** the last accepted time step is stored; a code is accepted only for a LATER step, in one conditional update.

### Throttling (all counted BEFORE the answer is sent)

| What                  | Rule                                                                                                                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TOTP codes            | Counter per person, separate from the password lockout (which a correct password clears). The 5th wrong code in a row locks for 60 s, doubling to 15 minutes; from the 20th in a row, **one try per 24 hours** |
| Recovery codes        | **Its own counter and lock**, so a locked TOTP counter never blocks a recovery code. The 5th wrong code in a row locks for 60 s, doubling, capped at 15 minutes; no 24-hour tier                               |
| Per challenge         | 5 TOTP tries and, separately, 5 recovery tries                                                                                                                                                                 |
| Per address           | the same shared limit as password sign-in on every public MFA route (`RATE_LIMIT_LOGIN_PER_IP`, default 10 a minute per route)                                                                                 |
| Attempts while locked | refused, not counted, nothing is checked                                                                                                                                                                       |
- A success clears that factor's counter; a successful recovery code also clears the TOTP counter. A password reset clears both counters and never removes the
  second factor.
- **TOTP is charged before it is checked.** The first statement locks the row, refuses when locked, charges the attempt and writes the audit row, and only then
  hands out the encrypted secret; success refunds it. Parallel guesses cannot outrun the counter.
- Guessing odds for somebody who already has the password: 3 valid codes in 10^6; with the 24-hour tier about 385 guesses in the first year, roughly **0.1 %**.
  (The password lockout's shape alone would allow ~35,000 a year, about 10 %.) A recovery code has 50 bits: not guessable at any of these rates.

### Recovery codes

10 codes of 10 characters (Crockford base32, shown as `XXXXX-XXXXX`), stored as keyed HMAC-SHA256 hashes, single use. Checking, counting, consuming and
auditing are ONE statement. Using one sends a security e-mail. (Regenerating them is Part 2: it needs the step-up.)

### Secrets at rest: a key of their own

`MFA_ENCRYPTION_KEYS=kid:secret,...` (first encrypts, all decrypt), NOT the signing ring: signing keys are retired after 90 days, these must live as long as one
row uses them.
- The TOTP secret is AES-256-GCM, random 12-byte nonce, **the user id as additional authenticated data** (a ciphertext copied to another person's row does not
  decrypt). Only the application decrypts; the database never sees the plain secret.
- Recovery codes use a separate key derived (HKDF, own label) from the same entry.
- Rotation: put the new key first, run `pnpm mfa:rekey` (re-encrypts the secrets). A recovery-code HASH cannot be re-keyed, so the old key stays until the
  command reports no row using its id.
- **The keys are backed up SEPARATELY from the database** (`docs/production-config.md`, `docs/backup-and-restore.md`). A database backup without them is
  useless to a thief, and so is a restored database to us: every enrolled administrator would be locked out until each one is reset. The restore drill restores
  MFA rows and decrypts them with the saved keys.

### Erasure and exports

Account erasure removes the person's second factor, recovery codes and challenges in the same transaction (trigger on `users.erased_at`, so every path of
erasure, including the re-application after a restore, is covered). A college-level erasure leaves them: they belong to the global account. No export, log or
audit row ever holds a secret, a code or an `otpauth://` link.

### Planned for Part 2

- **Step-up** (`config: { stepUp: true }`): a second-factor verification at most 10 minutes old, otherwise `403 mfa_step_up_required`. On member role change /
  suspend / reactivate / remove / unlock, inviting an institution admin, erasure approve / reject / cancel, every platform write and the audited platform view of
  a college's members, gradebook unlock, and the person's own password change, authenticator replacement, new recovery codes and disable. The list is pinned by
  a test.
- **Reset after losing device and codes**: platform administrators only, filer ≠ approver ≠ subject (so **three platform administrators** are needed),
  `pending_approval -> approved -> done`, executed 24 hours after approval, undecided requests expire after 7 days, cancelled by a successful sign-in of the
  subject. Execution removes the factor, revokes every session and invalidates the password. Break glass: `pnpm mfa:reset --email` over the owner connection.
- **Disable** is refused while the role requires the factor.

## Consequences

- An administrator needs a working mailbox AND the password to enrol, and an authenticator app afterwards.
- Losing `MFA_ENCRYPTION_KEYS` locks out every enrolled administrator.
- Password sign-in still costs 2 round trips; the code step 2, a recovery code 1.
- Lock order for everything that touches these rows: `user_credentials` -> `user_mfa` -> challenge -> sessions (the same order as account erasure, so the two
  cannot deadlock).

## Not built / limits

No WebAuthn / passkeys (phishing-resistant, a later step); TOTP can be phished in real time. No opt-in for members. The authenticator secret is shown once at
enrolment and cannot be read back.
