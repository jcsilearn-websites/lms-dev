# Production configuration (Cloud SQL and friends)

Settings the production environment must carry that no migration or environment variable of the app can enforce on its own.
The deploy checklist of the GCP step starts here: first the full list of environment variables, then the settings a variable cannot carry.

## Environment variables and secrets (API, worker, migrate)

Every variable the three processes read, from their schemas in `backend/src/config/env.ts` (`apiEnvSchema`, `workerEnvSchema`, `migrateEnvSchema`, plus
`ownerEnvSchema` for the owner scripts). **`backend/src/config/__tests__/production-config-doc.unit.test.ts` fails when a variable of a schema is not in a table
below**, so this page cannot silently fall behind the code. Each value is validated at start-up; a refusal names the variable and never echoes a value.

- **API** (`pnpm start`, `dist/server.js`), **worker** (`pnpm start:worker`, `dist/worker.js`) and **migrate** (`pnpm db:migrate`, run by the deploy with the OWNER connection) are
  three separate processes. The API and the worker share most variables: give them the SAME secrets, above all `SIGNING_KEYS` and `SUPPRESSION_HASH_KEYS`. Only the API reads the
  HTTP block; only the worker reads its health port.
- **Secrets** (Secret Manager, mounted as environment variables): `DATABASE_URL`, `DATABASE_APP_URL`, `LMS_APP_PASSWORD`, `SIGNING_KEYS`, `SUPPRESSION_HASH_KEYS`, `METRICS_TOKEN`,
  `SMTP_USER` and `SMTP_PASSWORD` or `SENDGRID_API_KEY`, and whichever of `STORAGE_SIGNING_SECRET`, `VIDEO_SIGNING_SECRET`, `NOTIFY_SIGNING_SECRET` and `DEADLINE_RECEIPT_SECRET` are
  used. Never commit one: `.env` is git-ignored and `.env.example` holds placeholders only.
- **The smallest production set** (everything else has a safe default). API and worker: `NODE_ENV=production`, `APP_BASE_DOMAIN`, `DATABASE_APP_URL`, `DB_SSL=verify-full` with
  `DB_SSL_CA`, `SUPPRESSION_HASH_KEYS`, `SIGNING_KEYS`, `EMAIL_PROVIDER` (with `SMTP_HOST` or `SENDGRID_API_KEY`), `EMAIL_FROM_DEFAULT`, `STORAGE_DRIVER=gcs` with `STORAGE_GCS_BUCKET`,
  `VIDEO_PROVIDER`, and `TRUST_PROXY=true` on the API. Migrate: `NODE_ENV=production`, `DATABASE_URL`, `DATABASE_APP_URL`, `LMS_APP_PASSWORD`, `DB_SSL` (with `DB_SSL_CA`).
  The GCS storage driver and both managed video providers are stubs until the GCP step, so a real production start is blocked on them on purpose.
- Generate a random secret: `openssl rand -base64 48` (32+ characters). A key list is `k1:<secret>`, or `k2:<new>,k1:<old>` while rotating.

## Cloud SQL for PostgreSQL 17: database flags

| Flag       | Value | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jit`      | `off` | The planner charges `disable_cost` to plan nodes our functions turn off (`enable_nestloop`, `enable_seqscan`); on a server built with LLVM JIT every inner statement is then JIT-compiled on every call (CI found it: gradebook tests 3-10+ s instead of ms). Small OLTP statements never profit from JIT. The per-function `SET jit = off` (migrations 0049, 0056) and the role default (migration 0058) already cover the app; the instance flag covers the owner role (migrations, `pnpm db:migrate`, ad-hoc work) and any other client. |
| `timezone` | `UTC` | Cloud SQL's default is already UTC; set it explicitly so a changed default can never move dates. `timestamptz + interval` and casts of a `timestamptz` to `date` use the SESSION zone; the app never sets one. Migration 0058 pins `lms_app` to UTC; the flag does the same for every other role. Anything that needs a calendar day or a wall-clock time uses the COLLEGE's zone explicitly (`lms.tenant_tz`, `lms.local_day`, the offering copy).                                                                                         |

```
gcloud sql instances patch <instance> --database-flags=jit=off,timezone=UTC
```

`--database-flags` REPLACES the whole flag list: read the current list first (`gcloud sql instances describe`) and pass every flag.
Setting `timezone` or `jit` needs no restart. The role settings of migration 0058 (`ALTER ROLE lms_app SET ...`) are applied by the
migration itself and need the migrating role to be allowed to alter `lms_app` (the same as the password handling of 0001).

## Verifying after a deploy

```
SHOW jit;        -- off
SHOW timezone;   -- UTC
-- as lms_app on a fresh connection: both again (test/app-role-defaults.test.ts does this against the test database)
```

## Data protection (step 14b): secrets and settings

| Variable                       | Where it lives                                                                                        | Required                                                                      | What it is                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SUPPRESSION_HASH_KEYS`        | **Secret Manager**, mounted as an env var in the API AND the worker (the worker executes the erasure) | **yes, when `NODE_ENV=production`** (the process refuses to start without it) | `kid:secret,kid:secret`, each secret 32+ random characters, ids `[A-Za-z0-9_-]{1,16}`. The keys of the KEYED HASH (HMAC-SHA256, HKDF label `lms.suppression-hash`) that records a suppressed e-mail address once its owner is erased (`email_suppressions.email_hash`, with the id of the key in `email_hash_kid`). | `ERASURE_LEDGER_DIR`           | a directory (development and CI only)                                                                 | no (default `.erasure-ledger`)                                                | Where the **erasure ledger** is written with the local driver. Generate a key: `openssl rand -base64 48`. Create the list as ONE secret value: `k1:<secret>`.

### Rotating `SUPPRESSION_HASH_KEYS` without losing a match

A stored hash cannot be re-keyed (the address is not kept), so an old key must stay as long as any row uses it:

1. Add the new key IN FRONT: `k2:<new>,k1:<old>`, deploy API and worker. New hashes use `k2`; every lookup tries `k2` and `k1`.
2. To know when `k1` may go: `SELECT * FROM lms.privacy_suppression_key_usage();` (key id and the number of rows that carry it).
3. Remove `k1` only when its row count is 0. Removing it earlier makes the suppressions hashed under `k1` unmatchable (an address that bounced could be mailed again).

A leaked key lets whoever has the database also test candidate addresses against the hashes (the usual limit of a hash of a low-entropy value):
rotate it as above, and treat `email_suppressions` as personal data in backups.

### The erasure ledger bucket (GCP step) and the backup of `SUPPRESSION_HASH_KEYS`

**The ledger bucket must be separate from the database backups.** A restore, a deleted backup bucket or a compromised backup role must not reach it:
its own bucket (ideally its own project), never the bucket of the Cloud SQL exports or the logical dumps. Required settings:

- **object versioning ON** (an overwritten or deleted line is still recoverable);
- a **retention lock** (a locked retention policy on the bucket: objects cannot be deleted or overwritten before it ends, and the policy cannot be shortened;
  the period is the one counsel agrees, at least as long as the longest backup that could be restored plus the academic records' period);
- the application's service account is **write-only** (`roles/storage.objectCreator`: it can add objects, not delete or overwrite them); the reader of the
  ledger is a separate identity used only by `pnpm privacy:reapply-erasures` (`roles/storage.objectViewer`);
- an alert on any delete or retention-policy change in that bucket's audit log.

The local driver (a JSON-lines file) is for development and CI only. An entry is written after the commit of its erasure; until the GCS driver exists the
write answers 503 and the request keeps `ledger_at` NULL, so the entry is retried by every scan and is never lost.

**`SUPPRESSION_HASH_KEYS` must be backed up, and what losing it means.** The keyed hash is one-way: the address is gone, so a lost key can never be
reconstructed or recomputed. Keep every key id and secret that ever signed a row you still have (Secret Manager: keep ALL versions; plus an offline copy
held by the owner, sealed, stored apart from the database backups). **If a key is lost:** the suppressions hashed under it become unmatchable, so an
address of an erased person that had bounced or complained could be mailed again if a new account is created with it (suppressions of live accounts keep
matching by their plain address). It cannot be repaired afterwards. Only remove a key from the list when `privacy_suppression_key_usage()` shows no row
under its id (rotation, above).

### The erasure ledger and a restore

The ledger (ids only: request, membership, user, college, level, time) is what makes an erasure survive a restore of an OLDER backup.
After ANY restore into a production database, once it is migrated and before it takes traffic (the ledger holds college entries and account entries; the
college ones come first in the file and are re-applied first, an account whose college erasure is still owed is reported as WAITING and the command exits
with code 2: run it again):

```
pnpm privacy:reapply-erasures --yes
```

It is idempotent. The restore drill (step 14b, backups) includes it. The Cloud SQL backup window (point-in-time recovery 7 days, logical dumps
30 days, see `docs/data-retention.md`) is what the erasure screens tell the member about backups.

## Logical backups and the restore (step 14b, part B)

Full procedure, targets and the drill: `docs/backup-and-restore.md`. What the GCP step has to provide:

- a scheduled job that runs `pnpm db:backup --out <mounted bucket path>` nightly with the **owner** connection (a separate service account; never the application's), in an image that has
  the **PostgreSQL 17 client tools** (`pg_dump`, `pg_dumpall`, `pg_restore`), and writes to a bucket **of its own**: not the erasure ledger's, encrypted, access-controlled, with a lifecycle rule
  that deletes objects at **30 days** (the window the erasure screens state). The `--keep-days` pruning of the script is for a plain disk;
- Cloud SQL point-in-time recovery on (7 days of log, 7 automated backups), the exact commands are in `docs/backup-and-restore.md`;
- after ANY restore or clone: `pnpm db:verify-roles --fix`, `pnpm db:migrate`, `pnpm privacy:reapply-erasures --yes`, and only then traffic. `LMS_APP_PASSWORD` must equal the password inside
  `DATABASE_APP_URL` (the role's password comes from the environment, never from a backup: dumps are written without role password hashes).
